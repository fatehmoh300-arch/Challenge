## الخلاصة التنفيذية
المشروع الحالي تطبيق أولي عامل البنية لتحدٍّ واحد يركز على العادات اليومية والقراءة والدعوات ولوحة ترتيب بسيطة. ليس بعد منصة متعددة التحديات عامة/خاصة وفق المواصفات الجديدة. توجد بنية تقنية قابلة لإعادة الاستخدام، ولا توجد حاجة لإعادة البناء من الصفر.

## ما تم التحقق منه
- مستودع GitHub موجود، والفرع `main` يحتوي على تطبيق Next.js 16 وReact 19 وTypeScript.
- آخر تشغيل GitHub Actions ظاهر في السجل كان ناجحاً، لكن ذلك لا يثبت صحة كل الوظائف في بيئة حية.
- مشروع Supabase `clwojdttvbembtfytrbi` حالته `ACTIVE_HEALTHY`.
- توجد 8 جداول عامة: profiles, challenges, challenge_members, habits, daily_logs, habit_completions, reading_logs, invitations. RLS مفعّل على الجداول الثمانية.
- سجل ترحيلات Supabase يثبت تطبيق migrations الثلاثة: challenge_schema وhardening_and_scoring وadvisor_hardening.
- قاعدة البيانات تحتوي حالياً على سجل واحد في profiles وchallenges وchallenge_members، وست عادات، ولا توجد سجلات إنجاز/دعوات بعد.
- مشروع Vercel باسم challenge موجود، وآخر نشر إنتاجي مرتبط بآخر commit على main وحالته READY. هذا يثبت اكتمال النشر، لا يثبت نجاح تدفق التسجيل أو عمل التطبيق end-to-end.
- الصفحة الجذرية الحالية `/` تحوّل الزائر مباشرة إلى `/dashboard`؛ لذلك لا توجد حالياً صفحة عامة لاستكشاف التحديات.
- مزود التطبيق يحمّل عضوية تحدٍّ واحدة فقط لكل حساب (أقدم عضوية)، ما يجعل دعم تعدد التحديات غير مكتمل في الواجهة.
- تقرير التنفيذ وREADME يحتويان بعض معلومات تشغيل قديمة أو متعارضة مع الحالة الحالية؛ يجب تحديثهما بعد اعتماد التغييرات.

## الموجود ويمكن إعادة استخدامه
- تسجيل الدخول وإنشاء الحساب عبر Supabase Auth، مع callback لتأكيد البريد.
- ملفات المستخدم الأساسية.
- تحدٍّ واحد، عضوية ودعوات برمز، عادات، سجلات يومية، إنجازات عادات، وسجل قراءة.
- لوحة ترتيب مبنية على بيانات الإنجاز، وقواعد نقاط واختبارات آلية.
- سياسات RLS وترحيلات أمنية، وPWA قابل للتثبيت بحدود موثقة.
- صفحات لوحة التحكم واليومي والتقويم والمنافسة والإحصائيات والمراجعة والإعدادات.

## الفجوات مقارنة بالمواصفات المعتمدة
### حرجة للنسخة الأولى
1. نموذج التحديات الحالي ضيق ومخصص لتحدٍّ واحد؛ لا توجد إدارة متعددة التحديات من حساب واحد.
2. لا توجد صفحة عامة لاستكشاف التحديات العامة، ولا حقول/سياسات مكتملة للفصل بين العام والخاص.
3. لا يوجد مسار مكتمل لإنشاء تحدٍّ مخصص بمدد وأنواع وقواعد قابلة للضبط، أو اقتراح تحدٍّ واعتماده.
4. لا توجد جداول أو واجهات للمنشورات والتعليقات والردود والتفاعلات والبلاغات.
5. لا يوجد مركز إشعارات داخلية أو إعدادات تفضيلات الإشعارات.
6. لا توجد ملفات شخصية عامة قابلة للتحكم في إظهار عناصرها، beyond الاسم والصورة الأساسيين.
7. أدوار العضوية الحالية تقتصر على owner وmember؛ لا يوجد تفويض مساعد/مشرف، ولا ينبغي توسيعه قبل وضع صلاحيات خادمية واضحة.
8. لا يوجد تحقق فعلي موثق لتدفقين مستقلين أو اختبار RLS/Auth end-to-end.

### موجود جزئياً أو مؤجل
- النقاط ولوحة الترتيب موجودتان في نطاق تحدٍّ واحد؛ الترتيب اليومي/الأسبوعي/الشهري والتاريخي لم يثبت اكتماله.
- إثبات الإنجاز المرن بالصور/الملاحظات غير مكتمل.
- PWA قابل للتثبيت، لكنه لا يوفر مزامنة offline.
- التذكيرات الحالية تعتمد على تشغيل التطبيق؛ لا يوجد Push مضمون عند إغلاقه.
- رفع الصور الشخصية غير مكتمل.
- المحادثات الخاصة والمجموعات الفرعية مؤجلة وفق القرار، ولا حاجة لبنائها الآن.

## ملاحظات أمنية من Supabase Advisors
- تنبيه INFO: جدول invitations لديه RLS ولا توجد سياسات مباشرة. قد يكون هذا مقصوداً لمنع الوصول المباشر واستخدام RPC آمنة؛ يجب فحص مسارات الدعوات قبل أي تغيير، وعدم إضافة سياسة واسعة لمجرد إسكات التنبيه.
- تحذير بشأن ست دوال SECURITY DEFINER قابلة للتنفيذ من authenticated. هذا ليس دليلاً تلقائياً على ثغرة؛ يجب مراجعة كل دالة، والتحقق من تثبيت search_path والتحقق الداخلي من العضوية والصلاحيات، والإبقاء فقط على منح EXECUTE المقصودة.
- تحذير حماية كلمات المرور المسرّبة معطلة في إعدادات Auth؛ يُوصى بتفعيلها من لوحة Supabase إذا كانت متاحة ضمن الخطة والإعدادات.
- مؤشرات الفهارس غير المستخدمة معلوماتية حالياً ولا ينبغي حذفها قبل وجود حمل فعلي وقياس.

## خطة التنفيذ المقترحة
### المرحلة 0 — تثبيت السلامة
- الاحتفاظ بالنسخة الحالية وعدم إجراء تغييرات تدميرية.
- اختبار إعدادات البيئة وAuth والنشر بحسابين منفصلين.
- مراجعة دوال SECURITY DEFINER وسياسات الدعوات، وتوثيق ما هو مقصود.
- اعتماد نموذج بيانات متعدد التحديات قبل بناء واجهات جديدة.

### المرحلة 1 — MVP متعدد التحديات
1. جعل الصفحة الرئيسية عامة، وإضافة قائمة/تفاصيل التحديات العامة.
2. توسيع نموذج challenges إلى عام/خاص، حالة، مدة، وصف، مستوى، قواعد، وحد المشاركين، مع ترحيل متوافق لا يكسر بيانات التحدي الحالي.
3. إنشاء مسارات إنشاء التحدي والانضمام العام/برمز/طلب موافقة.
4. تعديل AppProvider والتنقل ولوحة المستخدم لدعم عدة تحديات واختيار التحدي النشط.
5. بناء صفحة تحدٍّ مستقلة تعرض الأهداف والتقدم والمنافسة.
6. إضافة منشورات وتعليقات وردود أساسية داخل صفحة التحدي، دون رسائل خاصة.
7. إضافة مركز إشعارات داخلية وتفضيلات بسيطة، مع تجنب Push والبريد في MVP.
8. إضافة إعدادات خصوصية الملف الشخصي الأساسية.
9. تثبيت آلية نقاط دورية وتراكمية وسجل غير قابل للتلاعب من الواجهة.

### المرحلة 2 — تحسينات بعد استقرار MVP
- شارات أوسع، إحصائيات تاريخية، رفع أدلة الصور، مراجعة الإنجازات، ومساعدون بصلاحيات محددة.

### المرحلة 3 — توسع مؤجل
- الرسائل الخاصة، المجموعات الفرعية، Push، وتحليلات أعمق.

## ضوابط التنفيذ
- كل تغييرات قاعدة البيانات عبر migrations جديدة، لا تعديل migrations المطبقة.
- الحفاظ على التحدي والبيانات الحالية وترحيلها إلى النموذج الجديد دون فقدان.
- عدم وضع service-role key في الواجهة أو المستودع.
- اختبار RLS من حساب مالك وحساب عضو وحساب غير عضو.
- اختبار واجهات الهاتف و50 عضواً كحمل تجريبي واقعي قبل الادعاء بتحمل هذا العدد.
- عدم شراء خدمات أو ترقية خطط قبل ظهور حاجة مقاسة.

## القرار التقني التالي
قبل كتابة migration للمنصة متعددة التحديات، يلزم اعتماد تصميم البيانات والصلاحيات المستهدف. لا توجد حاجة إلى تدخل المستخدم الآن؛ الخطوة التالية هي مراجعة دوال SQL الحالية وتصميم ترحيل توسعي متوافق مع البيانات القائمة، ثم عرضه في Pull Request قابل للمراجعة قبل دمجه.
