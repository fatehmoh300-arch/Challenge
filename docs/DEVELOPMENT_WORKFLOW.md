# سير العمل البرمجي

## الفروع

يُمنع العمل المباشر على `main`. أنشئ فرعاً لكل تغيير:

- `feat/<short-name>` للميزات.
- `fix/<short-name>` للإصلاحات.
- `security/<short-name>` للتغييرات الأمنية.
- `docs/<short-name>` للتوثيق.
- `chore/<short-name>` لأدوات وتهيئة المشروع.

ابدأ دائماً من الفرع الصحيح، وراجع حالة Pull Requests المفتوحة قبل إنشاء فرع جديد لتجنب تكرار العمل أو البناء على نسخة قديمة.

## Pull Request

يجب أن يحتوي PR على:
1. المشكلة أو النتيجة المطلوبة.
2. ما تغيّر ولماذا.
3. الاختبارات التي شُغّلت ونتائجها.
4. ما لم يُختبر بعد.
5. تغييرات قاعدة البيانات أو إعدادات الخدمات المطلوبة.
6. مخاطر الخصوصية والأمان والتوافق مع البيانات التاريخية.

لا تدمج PR مسودّة، ولا تعتبر نجاح البناء وحده قبولاً للميزة.

## قاعدة البيانات

- افحص migrations الموجودة وسجل الإصدارات في Supabase قبل إضافة أي migration.
- لا تعِد تنفيذ migration سبق تسجيله.
- لا تفترض أن بيئة Preview تستخدم قاعدة منفصلة عن الإنتاج.
- لا تنفذ اختبارات كتابة على بيانات الإنتاج. استخدم معاملة متراجعة أو بيئة اختبار مخصصة.
- افحص RLS وGRANT وRPC وقيود المفاتيح الأجنبية معاً.
- أي جدول أو دالة جديدة يجب أن تخضع لمراجعة صلاحيات صريحة؛ سجل المشروع يذكر قيوداً على تعديل default ACL لمالك قاعدة البيانات.

## أسلوب التطوير

- نفّذ تغييراً صغيراً قابلاً للمراجعة.
- أضف اختبارات انحدار للسلوك المهم، بما فيه الرفض وليس النجاح فقط.
- تجنب إعادة التنسيق الشامل أو إعادة الهيكلة غير المطلوبة.
- حدّث الوثائق عندما تتغير طريقة التشغيل أو حالة التنفيذ.
- لا تُدخل اعتماديات جديدة قبل تبرير فائدتها وكلفتها وتأثيرها على حجم الحزمة.
